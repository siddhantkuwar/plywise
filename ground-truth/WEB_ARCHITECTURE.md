# Web Architecture

## Decision

Plywise will use a hybrid web architecture:

- React is delivered as a normal website.
- Free Stockfish compute runs in the browser where supported.
- C++ validates chess and engine data and creates canonical Plywise reviews.
- PostgreSQL supports accounts and cross-device history.
- Hosted C++/Stockfish workers are optional for deep or batch work.
- The existing local application remains a reference mode during migration.

This decision avoids tying free analysis cost directly to user growth while preserving the C++
system as the source of chess truth.

## Deployment shape

```text
Static web host/CDN
  React + CSS + browser engine assets
           │
           │ HTTPS + event stream
           ▼
API edge / reverse proxy
           │
           ▼
C++ application service
  authz, imports, validation, reviews, profiles
      │                    │
      ▼                    ▼
PostgreSQL             analysis queue
                            │
                            ▼
                     C++ Stockfish workers
```

The first private deployment may use one service container and one database. The interfaces must
allow workers to separate later without pretending the system already needs distributed
infrastructure.

## Engine modes

### Quick

- Browser Stockfish lite build.
- Single thread.
- Conservative depth/time.
- Small initial download.
- Default compatibility option.

### Balanced

- Browser Stockfish profile selected from benchmark evidence.
- May use multithreading only when required headers and browser capabilities are present.
- Explicit CPU/battery warning on constrained devices.

### Deep

- Optional hosted Stockfish worker.
- Queued, bounded, and cost metered.
- Stronger search or MultiPV.
- Not required for the free core experience.

The product presents understandable profiles first. Advanced UCI settings are progressive
disclosure.

## Browser analysis contract

Conceptual request:

```json
{
  "analysisRunId": "opaque",
  "gameId": "opaque",
  "profile": "quick",
  "engine": {
    "name": "Stockfish",
    "version": "versioned-build",
    "source": "browser"
  },
  "positions": [
    {
      "ply": 12,
      "fen": "validated canonical FEN",
      "multipv": 1,
      "limit": {"kind": "depth", "value": 12}
    }
  ]
}
```

Conceptual observation:

```json
{
  "analysisRunId": "opaque",
  "ply": 12,
  "fen": "same canonical FEN",
  "depth": 12,
  "nodes": 123456,
  "timeMs": 420,
  "lines": [
    {
      "rank": 1,
      "centipawns": 34,
      "mate": null,
      "moves": ["e2e4", "e7e5"]
    }
  ]
}
```

The production contract must include size limits, idempotency, sequence/completeness rules, engine
hash, and structured errors.

## Trust boundary

Browser engine observations may be malformed, forged, incomplete, replayed, or generated by a
different engine. C++ must:

- match account or guest ownership;
- match the analysis run and canonical FEN;
- bound numeric values and payload sizes;
- validate best moves and principal variations;
- enforce profile limits;
- reject duplicate or stale sequences safely;
- record execution source and engine identity;
- run Plywise classification itself.

Plywise does not need to prevent a user from lying to themselves, but shared infrastructure and
cross-game intelligence must not be corruptible by arbitrary payloads.

## Persistence migration

### Current

The local runtime builds one repository projection from an append-only event log in one data
directory.

### Target interfaces

- `IGameRepository`
- `IAnalysisRepository`
- `IJobRepository`
- `IProfileRepository`
- `IPracticeRepository`
- `ISettingsRepository`

Adapt names to the existing code. Avoid a mechanical interface explosion where one cohesive
transaction would be split into unsafe calls.

### PostgreSQL rules

- Opaque external IDs.
- Account ownership and foreign keys.
- Unique canonical import keys.
- Versioned analysis runs.
- Idempotency constraints.
- Transactional game and ownership creation.
- Explicit retention timestamps for guests.
- Migration history in source control.
- Tested backup, export, deletion, and restoration.

## Authentication

The initial implementation may use a managed authentication provider. Plywise stores the provider's
stable subject, not passwords.

The C++ service validates signed access tokens and performs resource authorization. Frontend route
guards are convenience only.

Extension authorization, when permitted, uses a short-lived handoff and a narrowly scoped account
token. Website access tokens are not placed in page URLs.

## Guest flow

1. Create an opaque temporary session.
2. Parse and validate a completed PGN.
3. Run Stockfish in a worker.
4. Submit observations for a canonical review.
5. Keep temporary retention visible.
6. Offer explicit save-to-account.
7. Transfer ownership idempotently after authentication.
8. Delete expired guest records.

The implementation should investigate keeping more of steps 1–4 entirely on device, but must not
move chess truth into TypeScript to achieve it.

## Security baseline

- TLS in deployed environments.
- Strict origin and content-security policies.
- Cross-origin isolation only where required by the chosen engine build.
- Least-privilege database and deployment identities.
- Per-IP, guest, account, and global admission limits.
- Bounded request and PGN sizes.
- Safe import redirects and upstream timeouts.
- No shell command construction from user input.
- No production secrets in the browser bundle.
- Cross-account integration tests.
- Audit logs without raw credentials or unnecessary PGN content.
- Dependency, container, and secret scanning.

## Cost controls

Measure:

- browser profile completion and failure rate;
- average analysis time by game length and device class;
- API requests and stored bytes per review;
- server engine CPU seconds;
- cache hit rate;
- queued and cancelled work;
- database growth per active account.

Do not create artificial scarcity around free browser analysis. Apply server limits where shared
compute or storage has a real cost.

## Migration order

1. Separate frontend origin configuration.
2. Extract repository seams without changing local behavior.
3. Add account IDs and authorization contracts.
4. Add PostgreSQL beside the event-log implementation.
5. Deploy the existing C++ engine path for the first hosted vertical slice.
6. Add browser Stockfish and observation validation.
7. Make browser analysis the free default after parity and compatibility evidence.
8. Retain server analysis as an explicit optional profile.
